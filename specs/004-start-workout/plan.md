# Implementation Plan: View & Start Workout

**Branch**: `004-start-workout` | **Date**: 2026-03-09 | **Spec**: [spec.md](./spec.md)

## Summary

Add day-based exercise grouping to workout templates (backend schema + seed changes), then build the mobile "View & Start Workout" flow: a tappable Active Programme card on the dashboard that shows the next scheduled day's exercises and lets the user start a workout session. Includes a "Resume Workout" CTA for in-progress sessions.

Two codebases are touched: `vital-forge-v1` (Rails API) for prerequisites, then `vital-forge-mobile-v1` (this repo) for the mobile UI.

## Phase 0: Research Summary

All unknowns resolved. See `research.md` for full decisions. Key findings:

1. **Resume detection**: The template detail endpoint already returns `has_active_workout` and `active_workout_id`. Use this instead of scanning `GET /api/v1/workouts` for resume detection.
2. **Day count**: `GET /api/v1/workouts` filtered client-side for completed workouts from active template → `count % days_per_week + 1`.
3. **Migration strategy**: Add `workout_template_day_id` to `workout_template_exercises`; retain `workout_template_id` column for backwards compat.
4. **Mobile endpoint bugs**: `startWorkout` and `completeWorkout` in `workoutsApi.ts` have wrong URLs — fix in this feature.

## Phase 1: Implementation Design

### Backend Implementation Order

#### Step 1 — Migration: Create `workout_template_days`

> ⚠️ **Learning checkpoint**: Walk through Rails migration generation before executing.

Generate with:
```bash
rails generate migration CreateWorkoutTemplateDays \
  workout_template:references day_number:integer name:string \
  estimated_duration_minutes:integer muscle_focus:string
```

The migration adds the table, unique index on `(workout_template_id, day_number)`, and NOT NULL constraints on `day_number` and `name`.

#### Step 2 — Migration: Add `workout_template_day_id` to `workout_template_exercises`

> ⚠️ **Learning checkpoint**: This migration involves a data step — existing exercises must be assigned to a Day 1 record before the NOT NULL constraint can be applied.

Generate with:
```bash
rails generate migration AddDayToWorkoutTemplateExercises \
  workout_template_day:references
```

Migration structure:
1. Add column as nullable (`null: true`) first
2. Data step: for each template, create a `workout_template_days` record for day 1, then update all existing exercises to point to it
3. Change column to `null: false`

#### Step 3 — Models

- New `WorkoutTemplateDay` model with validations and associations
- Update `WorkoutTemplate`: add `has_many :workout_template_days`
- Update `WorkoutTemplateExercise`: add `belongs_to :workout_template_day`

#### Step 4 — Seeds: Full per-day exercise data

Re-seed all split templates with complete per-day exercise lists. See `data-model.md` for the full breakdown. Add missing exercises to the catalogue (Romanian Deadlift, Leg Curl as needed).

**Seed strategy**: Idempotent — use `find_or_create_by!` on days and exercises. Can be run multiple times safely.

#### Step 5 — Update `WorkoutTemplateStarter`

Add `day_number` parameter. Filter exercises via the day join:
```ruby
@template.workout_template_days
  .find_by!(day_number: @day_number)
  .workout_template_exercises
```
Default `day_number: 1` if not provided.

#### Step 6 — Update `WorkoutsController#start_from_template`

Pass `params[:day_number]` (defaulting to 1) through to `WorkoutTemplateStarter`.

#### Step 7 — Update `WorkoutTemplatesController#show`

Change `serialize_template_with_exercises` to nest exercises under days:
```ruby
template.workout_template_days.includes(workout_template_exercises: :exercise).map do |day|
  { id: day.id, day_number: day.day_number, name: day.name,
    estimated_duration_minutes: day.estimated_duration_minutes,
    muscle_focus: day.muscle_focus,
    exercises: day.workout_template_exercises.map { |wte| serialize_exercise(wte) } }
end
```

Update `includes` in `set_workout_template` to eager load the new association chain.

#### Step 8 — RSpec Tests

New and updated specs — see test design below.

### Mobile Implementation Order

#### Step 9 — Update `templatesApi.ts` types

Replace `WorkoutTemplateDetail` flat `exercises` with nested `days`:
```typescript
export type WorkoutTemplateDay = {
  id: number;
  day_number: number;
  name: string;
  estimated_duration_minutes: number | null;
  muscle_focus: string | null;
  exercises: TemplateExercise[];
};

export type WorkoutTemplateDetail = WorkoutTemplate & {
  has_active_workout: boolean;
  active_workout_id: number | null;
  days: WorkoutTemplateDay[];
};
```

Also update `WorkoutTemplate` base type to include `has_active_workout` and `active_workout_id` (returned by the list endpoint too).

#### Step 10 — Update `workoutsApi.ts`

Fix endpoint URLs and update `startWorkout` mutation signature:
```typescript
// Before (wrong)
startWorkout: builder.mutation<any, { workout_template_id: number }>({
  query: (body) => ({ url: '/api/v1/workouts', method: 'POST', body }),
})

// After (correct)
startWorkout: builder.mutation<WorkoutSession, { templateId: number; day_number: number }>({
  query: ({ templateId, day_number }) => ({
    url: `/api/v1/workout_templates/${templateId}/start`,
    method: 'POST',
    body: { day_number },
  }),
})

// Also fix completeWorkout (wrong: POST /finish → correct: PATCH /complete)
completeWorkout: builder.mutation<any, number>({
  query: (workoutId) => ({
    url: `/api/v1/workouts/${workoutId}/complete`,
    method: 'PATCH',
  }),
})
```

Add explicit `Workout` response type covering `id`, `completed`, `started_at`, `workout_template_id`, `workout_exercises`.

#### Step 11 — Update `home.tsx`

Add three new behaviours:

**a) Fetch template detail**
```typescript
const { data: template } = useGetTemplateQuery(
  preference?.selected_workout_template_id ?? 0,
  { skip: !preference?.selected_workout_template_id }
);
```

**b) Fetch workouts + compute next day**
```typescript
const { data: workouts = [] } = useGetWorkoutsQuery();
const completedCount = workouts.filter(
  w => w.workout_template_id === preference?.selected_workout_template_id && w.completed
).length;
const nextDay = (completedCount % (preference?.training_days_per_week ?? 1)) + 1;
const nextDayName = template?.days?.find(d => d.day_number === nextDay)?.name ?? `Day ${nextDay}`;
```

**c) Conditional card render**
- `template?.has_active_workout` → show Resume CTA (orange `primary` Button)
- Otherwise → make Active Programme card a `Pressable` → navigate to `/workout-preview` with `{ templateId, dayNumber: nextDay, dayName: nextDayName }`

#### Step 12 — New screen: `app/workout-preview.tsx`

**Route**: `/workout-preview`
**Params**: `templateId: string`, `dayNumber: string`, `dayName: string`

Screen structure:
```
<Screen>
  <Card>  ← programme header
    programme name, goal chip, experience chip
    "Day {N} — {dayName}" label
  </Card>

  <FlatList>  ← exercise list (Constitution VII)
    data={day.exercises}
    renderItem={ExerciseRow}
    keyExtractor={item => item.id.toString()}
  </FlatList>

  <Button variant="primary" title="Start Workout" />  ← sticky bottom
</Screen>
```

`ExerciseRow` component (inline, not extracted — single use):
- Exercise name (`typography.subtitle`)
- Muscle group chip (`colors.lightBlue` background)
- `{recommended_sets} sets` badge

On "Start Workout" tap:
1. Call `startWorkout({ templateId, day_number: dayNumber })`
2. Disable button + show loading indicator
3. On success → `router.replace('/workout-active')` passing `workoutId` (Feature 005 placeholder: navigate to `/home` with a success toast until 005 is built)
4. On 409 → `Alert.alert` offering to resume (`router.push('/workout-active', { workoutId: active_workout_id })`)
5. On other error → `Alert.alert` with retry

#### Step 13 — Register route in `_layout.tsx`

Add `<Stack.Screen name="workout-preview" options={{ title: 'Today\'s Workout' }} />` to the root Stack.
