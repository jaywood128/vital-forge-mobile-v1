# Implementation Plan: 010 — Password Reset

**Branch**: `010-password-reset` | **Date**: 2026-05-16 | **Spec**: `specs/010-password-reset/spec.md`

## Summary

Add a forgot-password / reset-password flow. User enters email → Rails generates a reset token (existing model methods) and sends a deep-link email → user taps link → Expo Router routes to `app/reset-password.tsx` with the token as a URL param → user sets new password (client-side validated) → navigated to login with a success banner. No migrations needed. Deep-link scheme already registered.

**Blocker before staging/production**: production SMTP provider must be configured.

## How the Token + Deep Link Flow Works

```
[User on login screen]
  → taps "Forgot your password?"
  → navigates to app/forgot-password.tsx

[Forgot Password screen]
  → user enters email → taps "Send Reset Link"
  → POST /api/v1/mobile/auth/forgot_password { email }
  → Rails: find user, call generate_password_reset_token!
      → writes SecureRandom.urlsafe_base64 to users.password_reset_token
      → writes Time.current to users.password_reset_sent_at
  → Rails: UserMailer.password_reset(user).deliver_later
      → email body contains: vitalforgemobilev1://reset-password?token=<token>
  → response always: { message: "If that address is registered..." }

[User opens email, taps link]
  → iOS/Android sees vitalforgemobilev1:// scheme
  → OS looks up which app registered this scheme → finds Vital Forge
  → opens app with URL: vitalforgemobilev1://reset-password?token=abc123...
  → Expo Router parses path (reset-password) + query param (token)
  → routes to app/reset-password.tsx
  → token available via useLocalSearchParams<{ token: string }>()
  → token is only in memory for the life of this screen — never written to storage

[Reset Password screen]
  → user enters new password + confirmation
  → client-side validation: min 8 chars, passwords match (before API call)
  → POST /api/v1/mobile/auth/reset_password { token, password, password_confirmation }
  → Rails: User.find_by(password_reset_token: token)
      → nil or expired → clear token (security), return 422
      → valid → user.update(password:, password_confirmation:)
               → clear token columns (update_columns nil, nil)
               → return 200
  → on success: router.replace({ pathname: '/login', params: { resetSuccess: '1' } })

[Login screen]
  → reads useLocalSearchParams() for resetSuccess param
  → shows one-time banner: "Password updated — please log in"
```

## Approach Tradeoffs

### Deep link vs OTP code

| | Deep link (chosen) | OTP code |
|---|---|---|
| UX | One tap from email | Manual code entry |
| Infrastructure | Scheme already registered | New field + short expiry + rate limiting |
| Security | 132-bit token | ~20-bit code (needs brute-force protection) |
| Email client risk | Custom schemes sandboxed in Gmail mobile | No risk |
| Backend work | Reuse existing token | New field, new validation logic |

**Decision**: Deep link. Reuses existing infrastructure. Gmail sandboxing is acceptable for MVP.

### Devise `:recoverable` vs custom token

| | Devise recoverable | Custom token (chosen) |
|---|---|---|
| Setup | Migration + module enable + existing method rework | Already exists, no migration |
| Token strength | ~90-bit (Devise.friendly_token) | ~132-bit (urlsafe_base64) |
| Expiry | Configurable (default 6h) | 2h hardcoded in model |
| Maintenance | Gem-maintained | App-owned |

**Decision**: Custom token. Already implemented with stronger entropy. No schema change needed.

### Return JWT on reset vs require re-login

| | Return JWT (auto-login) | Require re-login (chosen) |
|---|---|---|
| UX | Seamless | One extra step |
| Security | Reset token acts as a login credential — elevated risk | Explicit credential entry required |
| Complexity | Must handle SecureStore write on unauthenticated screen | None |

**Decision**: Require re-login. Simpler and more secure.

### Client-side validation: on blur vs on submit

| | Validate on blur | Validate on submit (chosen for first-attempt) |
|---|---|---|
| UX | Instant feedback | Feedback on first attempt only |
| Complexity | Need blur state tracking per field | Simple: check before API call |
| Convention | Common in web forms | Common in mobile forms |

**Decision**: Validate on submit attempt, then keep errors visible as user types corrections. This avoids showing errors before the user has finished typing.

## Known Issues in Existing Backend Code

### `password_reset_expired?` nil guard

The existing method:
```ruby
def password_reset_expired?
  password_reset_sent_at < 2.hours.ago
end
```

If `password_reset_sent_at` is nil (user has never requested a reset), this throws `NoMethodError`. The controller guards against this by checking `user.nil?` first, but if a user is found with a nil token, it could still raise. The controller should explicitly check:

```ruby
return 422 if user.nil? || user.password_reset_token.nil? || user.password_reset_expired?
```

### Clear token on expiry

Currently the plan only clears the token on success. On expiry detection, the controller should also clear the token:

```ruby
if user.password_reset_expired?
  user.update_columns(password_reset_token: nil, password_reset_sent_at: nil)
  render json: { error: "Reset link is invalid or has expired." }, status: :unprocessable_entity
  return
end
```

This prevents repeated probing of an expired token.

## Production SMTP — SendGrid ✅ (decided)

Development uses MailCatcher on `localhost:1025` — already configured and working.

**Provider: SendGrid** — free trial, then $20/month (Essentials). Emails sent from `noreply@forge-fitness-journal.app`.

### One-time DNS setup (outside code — ~30 min)

1. Create SendGrid account → Settings → Sender Authentication → Domain Authentication
2. Enter `forge-fitness-journal.app` → SendGrid generates CNAME + SPF DNS records
3. Add those records to your domain registrar's DNS panel
4. Click "Verify" in SendGrid — emails will now deliver as `noreply@forge-fitness-journal.app` with valid DKIM signature (prevents spam folder)

**Without domain auth**, emails send from a SendGrid-owned address and frequently land in spam. Do this before any user-facing test.
